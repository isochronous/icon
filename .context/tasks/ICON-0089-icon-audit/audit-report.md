## Executive Summary

**Overall health: FAIR.**

ICON came through the largest interval in its history — a breaking 2.0.0 release adding GitHub-only conversion, a `.context` knowledge graph, session-per-phase execution, model-aware isolated delegation, a second harness hook, a security CI stage, and seven new pre-commit gates — with **every mechanical invariant it gates passing clean and every defect this cycle sitting in ungated space**. That correlation was observed independently, without co-ordination, by three domains (01 Observation 1, 04 Observation 2, 05 Observation 2), and it is the single most important structural result in the report. Where ICON has built a gate, the class went to zero and stayed there: 50 of 50 skills registered against the `O-V1` gate, `common-constraints` byte-equal across all 9 agents, script parity byte-identical across all 6 copies, `context-graph --check` clean at 49 nodes, `check-rules-index` clean, `structural-check.sh` 5/5, zero dead `.context/` references, zero residual GitLab/Jira terms in `agents/` or `skills/`. ICON-0058's headline prescription — *"the codebase needs mechanical reach-at-the-moment-of-need infrastructure more than it needs more prose"* — was executed, and all five Focus-2 discoverability mechanisms shipped.

The verdict nonetheless moves down from STRONG, and the honest reason is two-part. **Five Critical findings exist where ICON-0058 found none**, and three of them are consumer-facing correctness defects in the init/upgrade tree that break a real `/icon-init` or `/upgrade-repo` run — one of which affects the *entire pre-2.0.0 installed base*. The other two sit on the release path, which force-moves `latest` into every consumer's plugin cache and currently passes **zero** mechanical gates while an ordinary commit passes ten. But the count movement itself needs care: three of the five Criticals are long-standing, not new, and the reason they were never found is that **`/upgrade-repo` has never been executed against ICON's own `.context/`** (schema 1.2 against a 1.12 template). The finding count went up eightfold *while the mechanical pass rate rose*. Under a displacement model those two facts contradict each other; under a detection-ceiling model they are the same fact. § *The Reach of Mechanization* argues the second reading and shows the first is falsified by ICON's own record.

The remaining issues cluster into four themes:

1. **The init/upgrade tree has one entry point and four divergent exit contracts.** `icon-init` unified the front door; nothing unified the back. The required-file set is written out in prose **six times**, and every Critical and Moderate parity finding in domain 03 is a divergence between two of those copies. This is also the cycle's clearest example of the mechanizability rule: *"root init must produce what leaf init produces"* is unmechanizable as prose and trivially mechanizable as a manifest.
2. **Enforcement strength is inversely correlated with consequence.** A logging helper gets a byte-parity gate; the credential-detection pattern list gets a comment. `.sh` files get shellcheck; `.ps1` files get nothing. Ordinary commits pass ten gates; the release — the only irreversible, all-consumers-at-once operation in the repo — passes none. And beneath all of it, the ten pre-commit invariants are **opt-in per clone, `--no-verify`-bypassable, and backstopped by no CI job whatsoever**. Every clean result quoted above is contingent on one config command.
3. **Session-per-phase was added alongside the model it replaced, not over it.** All four of domain 02's net-new Moderates are *seams* — the superseded phase-selection model still stated in the router, the fallback plan format missing the two sections all five phase skills fail closed without, the shipped template's "core sections" enumeration excluding them, and the close-gate's evidence artifact (`## Review Checkpoint`) defined in no template at all.
4. **The audit's own feedback loop is the least-mechanized surface in the system, and it failed end to end.** Four of six pre-assigned follow-up IDs were consumed by unrelated work, `gh issue list --state all` returns `[]`, no brief reads the dispositions table the skill itself produces, and the filing target is still GitLab. The recommended work all got done anyway — under different IDs, by a mechanism that is not the ledger.

**On the user's directive.** The script-offload analysis is not an appendix here; it is § *Consolidated Script-Offload Roadmap*, and it consolidates **34 upstream candidates into 20 ranked entries plus 2 prerequisites**, with stated ranking criteria, an enforcement venue per item, and an explicit not-worth-building list. Two conclusions matter more than the list. First, **the reach of mechanization is larger than the "no grep can see this" framing implies, because the limiting factor is representation, not detection** — a class becomes mechanizable exactly when its invariant has something to compare against. Second, **the two prerequisites come before any new gate**: amend ADR-005 (which is `Status: Accepted` and asserts premises every roadmap item contradicts), and add one CI job re-running the existing ten invariants. Adding an eleventh gate to an unbacked, bypassable, opt-in-per-clone stack raises surface without raising guarantee.

## Critical Findings (5)

All five are domain-owned and correctly tiered there; the cross-cutting pass added none. Three are consumer-facing (C1–C3, domain 03); two are release-path (C4–C5, domain 05).

### C1 — `upgrade-repo` misclassifies every pre-ICON-0080 stock `task-workflow-template.md` as CUSTOMIZED

*(native ID `C-89-03-01`, domain 03)*

- **Location**: `skills/upgrade-repo/SKILL.md:119-145` (bash and PowerShell branches); trigger commits `3418e84` (ICON-0080), `2866f2b` (ICON-0081).
- **Problem**: Phase 1's deprecation check decides "stock vs customized" by diffing the consumer's installed file against the **current** `$TEMPLATE_DIR` copy. That is only correct if the shipped template is frozen — and `context_template/context/workflows/task-workflow-template.md` has been edited **twice since it was deprecated** (`CHANGELOG.md:259-260`): once for the GitHub conversion, and once to prepend two `<!-- context-graph:orphan-ok -->` lines *purely to satisfy ICON's own pre-commit graph gate*. A consumer who installed a byte-perfect stock copy at any earlier version therefore diffs non-empty and is classified `deprecated (CUSTOMIZED)`.
- **Risk**: The misclassification cascades. Phase 2 (`:196-204`) invokes `merge-phase-templates`, which reads the delta backwards (`skills/merge-phase-templates/SKILL.md:28-34`) — newer stock content appears as *custom deletions* — so Step 4 (`:60-66`) asks the user to adjudicate sections they never removed and Step 5 (`:72`) withholds the deletion confirmation until they do. A routine `/upgrade-repo` becomes an interactive interrogation about a file the consumer never touched, and the deprecated file is never deleted. **This affects the entire pre-2.0.0 installed base.** The failure is additionally hidden by `m-89-03-01`'s `> /dev/null 2>&1` on the same `diff`, which swallows the error when `$TEMPLATE_DIR` is unset or the file is absent.
- **Fix**: Replace "does this equal HEAD's template?" with "does this file's sha256 appear under *any* recorded schema version?" — a per-release stock-hash registry emitted by `bump-versions.sh` (roadmap **R-7**). Correct for every historical consumer and generalizes to every version-markered template file. In the interim, drop the `2>&1`.
- **Cross-cutting note**: this is the cycle's sharpest instance of a systemic cost — **a suppression marker added as the minimum-effort way to make one gate green is the proximate cause of a Critical in another skill.** See § *What the roadmap costs*, item 2.

### C2 — `initialize-monorepo` `.sln` project discovery uses GNU-only `grep -oP`; returns zero projects on macOS/BSD

*(native ID `C-89-03-02`, domain 03)*

- **Location**: `skills/initialize-monorepo/SKILL.md:82` — `| grep -oP '"[^"]+\.csproj"' | tr -d '"' \`.
- **Problem**: `grep -P` (PCRE) is a GNU extension. BSD/macOS `grep` rejects it outright, as does busybox. This is the `.sln`-parsing path that enumerates the sub-projects a .NET monorepo init will initialize.
- **Risk**: Consumer-facing and **silent**. A macOS user runs `/icon-init` on a `.sln`-rooted monorepo, confirms `monorepo` at Step 3, and gets a root `.context/` with an empty `projects.md` and no sub-project context — with no error indicating why, because `initialize-monorepo` proceeds to dispatch per-area initialization for zero areas. `.context/standards/shell-portability.md` exists precisely to prevent this class and does not currently name `grep -P` among its six rules.
- **Fix**: `grep -oE '"[^"]+\.csproj"'` is an exact POSIX ERE equivalent here — no PCRE feature is used. One character of the fix; the durable form is roadmap **R-2**, whose deny-list also catches M-89-03-01, M-89-03-04, and the `python3` class. **R-2 is the cheapest Critical-preventing item in the report.**

### C3 — `context-specialist-impl-root` never creates the root-level `claude.md` redirect

*(native ID `C-89-03-03`, domain 03)*

- **Location**: `skills/context-specialist-impl-root/SKILL.md:94-107` (Step 4), `:289-303` (Step 15 verify) — zero occurrences of "redirect" in the file. Compare `skills/context-specialist-impl-leaf/SKILL.md:42-59`, `:313`; verified against `skills/upgrade-repo/SKILL.md:624`.
- **Problem**: `impl-leaf` creates and verifies a root-level `claude.md` redirect because, as it states at `:42-44`, "Copilot CLI loads a root-level `claude.md` when one exists, but does **not** automatically read `.claude/claude.md`." `impl-root` Step 4 handles `.claude/claude.md` only. `impl-root` is the skill **every** monorepo, workspace, and multi-module root runs — all three orchestrators load it by name (`initialize-monorepo` Step 5, `initialize-workspace` Step 6, `initialize-multimodule` Step 7).
- **Risk**: Copilot CLI users working at a monorepo/workspace/multi-module root receive **no project instructions at all**, on exactly the repo shape where root-level orientation matters most. It also makes init output structurally non-conformant with ICON's own upgrade contract: `upgrade-repo` Phase 4 item 6 verifies "Root-level `claude.md` exists," so a freshly initialized root fails its own verification the first time `/upgrade-repo` runs on it. ADR-004 is the governing decision this violates.
- **Fix**: Add the redirect creation and its verify item to `impl-root`. The durable fix is the manifest (**O-S2** / roadmap **R-5**) — this defect is one of five obligations `impl-root` has silently fallen behind `impl-leaf` on (M-89-03-02), and the reason nothing noticed is that the required-file set exists as prose in six places and as comparable data in none.

### C4 — The release flow tags and force-moves `latest` with no CI-status gate

*(native ID `C-I-1`, domain 05)*

- **Location**: `.claude/skills/release-plugin/SKILL.md:244-253` (Step 9: `git tag "v$NEW"` / `git tag -f latest` / `git push origin main "v$NEW"` / `git push -f origin latest`); Error Conditions table at `:281-289`.
- **Problem**: Nothing checks whether the `security` workflow passed on the release commit. A repo-wide grep for `gh run` / `gh workflow` / `check-runs` across `.claude/skills/release-plugin/` and `CONTRIBUTING.md` returns **nothing**, and the Error Conditions table has rows for "not on main", "dirty tree", and "push fails" but none for "CI is red". Step 8 (`:213-230`) commits directly to `main` and Step 9 pushes immediately, so there is no window in which CI could run on the release commit before `latest` moves even if someone wanted to look.
- **Risk**: `latest` is the marketplace's `ref`; force-moving it is the propagation mechanism into every consumer's plugin cache on their next update. A release is a one-way broadcast with no staged rollout and **no documented rollback**. The failure is not hypothetical: `.context/retrospectives.md:12` records that the `security` CI (semgrep SAST) *"had been RED on every PR and on `main` for many cycles, unnoticed until the user asked… 3 real findings, not a config error."* Any release cut in that window would have force-moved `latest` onto a commit with three live SAST findings, and nothing in the flow would have said so. The flow's only quality signal is the releasing agent's judgment, which ICON-0087 proved does not reliably notice a red check.
- **Fix**: `release-preflight.mjs` as Step 0 and again immediately before Step 9 (roadmap **R-1**), asserting branch/tree/sync state, `latest` resolves, `gh run list --branch main --commit $(git rev-parse HEAD)` shows `security` green, JSON validity, template version == released+1, and the CHANGELOG dedup `awk` returns empty. Plus an **Emergency rollback** section: how to re-point `latest` at the prior release tag and what consumers see in the interim.

### C5 — No mechanical JSON-validity gate exists anywhere for `.claude-plugin/plugin.json`

*(native ID `C-I-2`, domain 05)*

- **Location**: `.claude/skills/release-plugin/scripts/bump-versions.sh:104` (`sed -i "s/\"version\": \"${OLD_ESC}\"/\"version\": \"${NEW}\"/"`); verification at `.claude/skills/release-plugin/SKILL.md:203-209`; the declared-but-unexecuted control at `.claude/claude.md:11-14` and `.context/decisions/005-no-build-step.md:19`.
- **Problem**: The manifest is mutated by a regex text edit on JSON, and the only post-write verification is a `grep` for the version line — **which succeeds on a file that no longer parses as JSON** (unbalanced brace, stray byte, truncation from a failed write). Coverage elsewhere is nil: `.githooks/pre-commit` is 975 lines and 10 gates with no JSON gate; `.github/workflows/security.yml:13-54` runs gitleaks, semgrep, and shellcheck with no JSON gate. The one documented validation — `python3 -c "import json; json.load(open('.claude-plugin/plugin.json'))"`, declared by ADR-005 as *the* runtime check for this repo — was verified **not to execute on the maintainer's own machine**: `python3` resolves to the Microsoft Store app-execution-alias stub, and real Python is at `/c/Python314/python` with no `python3` alias.
- **Risk**: An unparseable `plugin.json` force-moved to `latest` breaks plugin load for **every** consumer, with no detection anywhere in the pipeline. Probability per release is low — `sed` on a stable one-line pattern is not fragile — but **detection probability is zero and blast radius is total and automatic**. The stated control has additionally been inert for an unknown period, which is the same silent-inertness shape as ICON-0087's unread CI.
- **Fix**: `scripts/check-json.mjs` (~40 lines of Node): `JSON.parse` every tracked `.json`, then assert `plugin.json` carries `name`/`version`/`description`, that `version` matches `^\d+\.\d+\.\d+$`, and that `$schema` is present. Wire it **twice** — `.githooks/pre-commit` armed on any staged `*.json` (fast, local) and a CI job in `security.yml` on every push (unbypassable, and the one that actually guards the release commit). Roadmap **R-1**. This closes C5 and makes ADR-005's own claim true for the first time.

### Ranking criteria (stated explicitly)

Five factors, scored, summed. **The scoring is a discipline for making trade-offs visible, not a precision instrument** — read the score as a band and read the *reasons* as the argument.

| Factor | 3 | 2 | 1 | 0 |
|---|---|---|---|---|

| **D — Displacement resistance** | — | **Anchored** — derives the expected value from a source of truth (a script constant, a directory listing, a manifest, a live CI status) | **Instance** — asserts a fixed string or shape an author can route around | — |

### Enforcement venue — the architecture, stress-tested

The four hosting options are **not interchangeable**, and the deciding property is *reach at the moment of need* — the meta-finding ICON-0058 named and that ICON-0060/0069/0088 have each attacked with more prose.

- **(i) `.githooks/pre-commit`** — fast, runs on every commit, already hosts ten gates that demonstrably work. Two defects: **opt-in per clone** (a clone without `git config core.hooksPath .githooks` silently enforces nothing) and **`--no-verify`-bypassable**.
- **(ii) GitHub Actions** — unbypassable, sees the whole tree and the pushed state. For **R-2** and **R-3** this is not a preference but a **correctness constraint**: their entire value is catching a site the current commit does *not* touch, and a staged-file-scoped hook is definitionally blind to that. `.claude/skills/icon-audit/SKILL.md:124,151` — GitLab residue two releases after the conversion — is a live instance no commit-scoped gate could ever have caught, because nobody has touched that file since. Its cost is the ICON-0087 failure mode: **a red check nobody reads is worth nothing**, so any new job must be paired with R-1's release-time consumption of `gh run` status.
- **(iii) Skill-invoked scripts** — run only when an agent remembers to invoke them, **reintroducing the exact reach problem the offload is meant to solve**. ICON already runs this experiment: `structural-check.sh` is skill-invoked and exhibits *both* predicted failure modes — it runs only when a human types the command (verified absent from CI), **and** its checks validate only the invoking skill's own files. Reach failure and scope failure in the same artifact. **Two justified exceptions only**, both where the trigger is genuinely a *workflow moment* rather than a file change: **R-1** (the release flow) and **R-8** (phase entry in a fresh session). Both must carry the reinforcement domain 05 prescribes — the invocation stated as the literal first action, `|| exit 1`, not as prose an agent may summarize.
- **(iv) Harness hooks** — unbypassable in-session and the right home for *runtime* controls (`guardrail-pretooluse.mjs` is correctly placed). But they are harness-specific — ADR-004 pressure, and `hooks/hooks.json:23`'s asymmetric `bash` key is already evidence of that friction — and they **must fail open**, which disqualifies them as correctness gates. Domain 05's own latent finding reinforces this: `guardrail-pretooluse.mjs:61` lowercases `toolName` for the `isBash` test while `:71`/`:104` test `writeTools.includes(toolName)` **case-sensitively**, so a harness emitting a differently-cased write-tool name would silently disable `secret-in-write` with **no signal**. That is exactly what fail-open means: correct today, silently wrong tomorrow, no alarm either way.

> **The rule: runtime safety → (iv), fail-open. Repo correctness → (i)+(ii), fail-closed. Workflow-moment procedures → (iii), and only with a (i) reminder behind them.**
>
> **With one sequencing dissent.** Domain 05 treats pre-commit's two defects as costs of an otherwise-working fast tier. X-89-3 establishes the stronger claim: with **no CI backstop for any of the ten invariants**, pre-commit is not the fast tier of a two-tier system — **it is the only tier, and it is advisory.** So the recommendation is ordered rather than parallel: **build R-0b before the eleventh gate.**

**On `.sh`/`.ps1` pairs vs a single portable `.mjs`.** The pair convention is a demonstrated drift source and a doubled maintenance cost — three `append-retrospective-entry` copies plus `context-graph` are held together only by a byte-parity gate that exists *because* they drifted; **R-16** exists because a second duplication was left unguarded; and `m-P-0089-5` is a third instance, where `check-rules-index.sh` ships without the `.ps1` sibling its neighbours have. The parity is also asymmetric in *quality*: CI shellchecks every `.sh` and **no PowerShell linter exists anywhere** (`m-I-9`), so half of each pair is verified and half is not. Meanwhile the `python3` the repo leans on for JSON work is **verified broken on the maintainer's own machine**, while **Node is a hard prerequisite of both harnesses and already the runtime of both shipped hooks** — and ICON-0012 already made exactly this call once, collapsing an `inject-manager-role.{sh,ps1}` pair into a single `.mjs`. **A single portable `.mjs` should be the default for every new deterministic check.** This is a **one-way door going forward, not a rewrite campaign**: no new `.sh`/`.ps1` pair; `.mjs` for anything new; existing pairs migrate opportunistically when next substantively edited. Blocked on **R-0a**, which currently rejects "a Node toolchain" on grounds two shipped Node hooks have already overtaken.

Twenty entries, six domains' worth of enthusiasm, and a maintainer who has to live with all of it. The costs, named honestly:

## The Reach of Mechanization

*The user's directive asked the hard version of the question, so the direct answer comes before the argument.*

> **Mechanization's reach is real, durable, and larger than the escalation evidence suggests — but only for gates anchored to a source of truth, and only up to the level of abstraction at which the invariant has a written representation.**

### Three closure mechanisms, sharply different durability

This comparison is only available from the synthesis seat, because each domain saw one facet.

**Tier 1 — a script gate. Closed once; stayed closed under maximum stress.** The README skill-registration class recurred across ICON-0046 and ICON-0058. **Two remedies were tried.** ICON-0060 shipped a **prose checklist** into `CONTRIBUTING.md`; the class had already recurred once by then and the checklist was not what stopped it. ICON-0080 shipped a **fail-closed gate**. Result this cycle: **50 of 50 skills registered, zero misses** — and `.context/retrospectives.md:43` records the gate *firing in anger* during the highest-churn task in the interval, when ICON-0080 renamed three skills and deleted three more: *"the README skill-registration gate blocked committing the renamed skills until README was updated."* **A rename storm is precisely the event that beat the prose checklist, and the gate held.**

**Tier 2 — a precise specification. Closed once, immediately, incompletely.** ICON-0058's recommendation for `ecological-impact` named four numbered edits with exact target lines, and ICON-0059 — the very next task — executed that specification. Where an earlier, vaguer handoff drifted to a different skill entirely, a sufficiently concrete recommendation did not. **But the sweep stopped at the files the recommendation named**: `README.md:162` still describes the skill as measuring "a **Copilot** session," thirty tasks later (`m-U-7`). **Precision buys a single execution; it does not buy a boundary.**

**Tier 3 — a process ledger. Did not function.** `X-89-1`: four of six pre-assigned IDs re-scoped, six issue links unreachable, no brief reads the table, the filing target a tracker ICON abandoned. The recommendations closed anyway — via Tier 2 in one case and via unrelated later tasks in the rest.

The ordering is unambiguous. But it does not license "mechanize everything," and the next three sections say why.

### The escalation is a detection ceiling, not a displacement

Domain 03 observed that ICON-0058 predicted a literal-grep gate would close sweep-incompleteness, that the prediction *"held in the affirmative"* — all five "the 15th" instances and all three "plugin-lint Check" instances swept clean — *"but the class did not disappear; it moved up a level of abstraction."* This cycle's equivalent findings are not stale literals but **stale obligations** (C3, `M-89-03-02`, `M-89-03-03`), which no literal grep can see.

**The synthesis lens supplies the correction that changes the conclusion: the gate was never built.** ICON-0015's O-V4 literal-grep gate remains unimplemented — now 4+ cycles — and only a *partial* implementation exists (one hardcoded literal, four bespoke regexes). **The literals were swept by hand, under ICON-0060.**

So the escalation happened **without** a gate. Whatever caused it, a gate did not. That falsifies the displacement hypothesis in its strong form and points at the real mechanism:

> **Fixing a failure class at level N does not create level N+1; it *reveals* it.**

The stale obligations in `impl-root` were there the whole time. ICON-0046 and ICON-0058 did not miss them out of carelessness — they were downstream of a noisier, cheaper-to-find class that consumed the audit's attention. Clear the literals and the audit's marginal attention moves down a layer, where it finds what was always there.

That reframing is not cosmetic; it changes the expected value of the roadmap:

- Under **displacement**, twenty gates buy twenty relocated failures and the program is close to worthless.
- Under **detection-ceiling**, twenty gates buy twenty permanently-closed classes *plus* visibility into a layer that was previously invisible — at the cost of an audit that must work harder and **will report more findings, not fewer, for several cycles**.

**The second model predicts exactly what this cycle observed**: 0 → 5 Criticals and 3 → 24 Moderates against a *rising* mechanical pass rate. Every gated invariant in the repo is clean while the finding count went up eightfold. Under the displacement model those two facts contradict each other. Under the ceiling model **they are the same fact**.

**The honest caveat**: "deeper inspection" cannot be fully separated from "genuine regression." The interval was the largest in ICON's history, and domain 02 makes the case crisply that all four of its net-new Moderates are *seams* left by session-per-phase — new work, incompletely swept. What can be said with confidence is that **the three domain-03 Criticals are not new**: `upgrade-repo` Phase 1's diff, `initialize-monorepo`'s `.sln` parsing, and `impl-root`'s missing redirect are all long-standing, and `M-89-03-07` proves *why* they were never found — **`/upgrade-repo` has never been executed against ICON itself.** They could only ever surface by someone reading the code, which is what happened this cycle.

### What is mechanizable in principle — a sharper line than "obligations aren't"

Domain 03 wrote that stale obligations are unmechanizable because *"there is no literal to grep for."* True as stated, slightly too pessimistic as a general claim. The precise version:

> **A class becomes mechanizable exactly when its invariant has a representation the checker can compare against.** Most of this cycle's "no grep can see this" findings are really *"no grep can see this **yet**, because the thing to compare against does not exist as a comparable."*

Tested against the actual findings:

- ***"Root init must produce what leaf init produces"*** — unmechanizable as prose, **trivially mechanizable the moment the required-file set is a manifest keyed by `tree_position`.** The obligation is currently written out in prose **six times**. Six copies is not "unrepresentable" — it is **"represented six times, comparably zero."** And the six-way prose duplication is simultaneously the *cause* of the drift (C3, `M-89-03-02`) and the *reason it cannot be checked*. This is the cycle's canonical case, and it is why **O-S2**'s manifest is scoped as a **prerequisite** rather than as another gate.
- ***"Every isolated specialist has a warmstart-in / report-out contract"*** — ADR-015 asserts it of seven agents; `manager-routing-guide:104-114` **already holds the authoritative roster as a table**. Parse the roster, assert the sections. Same shape as the one gate that survived a rename storm.
- ***"The removal is complete"*** — unmechanizable as a judgment, mechanizable as `banned-literals.json` + whole-tree CI. The obligation is even **written down twice in the retrospective log** as *"give sweep coders a whole-tree grep mandate"* — **which is a script specification expressed in English.**

This is why three domains independently converged on **declarative data + thin checker** (**O-S1**). **The bottleneck is not checker technology. It is that ICON's invariants live as prose restated at N satellite sites, and prose restated at N sites is the cause of the drift as well as the reason it cannot be checked.** ICON-0088 promoted exactly this rule — *"Satellites point by reference; only the canonical site enumerates"* — and then, **in the same entry**, recorded that it was *"Caught by @reviewer, not by any gate."* The rule and its own unenforceability shipped together.

### What is genuinely NOT mechanizable

Three categories. **Every domain drew the line in the same place without co-ordination** — all five wrote an explicit residual-judgment section and domain 01 added a rejected-candidates note. That uniformity is itself evidence the line is real.

1. **Truth about the world, as opposed to internal consistency.** `M-U-1`'s worked example disagrees with its own formulas by 1000× — that *is* mechanizable, and **O-V4** (generate the example from the constants) is the right answer. But whether 0.001 kWh per 1,000 tokens is the *correct* constant, when the skill's own cited basis implies ~57× less, is a claim about energy consumption. **A script can make a document self-consistent; it cannot make it true.** Note the sharp implication, which changes the order of operations: **generating the example would have made the skill consistently and confidently wrong — the 1000× internal break is currently the only visible symptom of the 57× external error.** Fix the constant first, generate second.
2. **Whether a rule should apply, and at what tier.** Accept-with-rationale vs trim (ADR-008); which section to extract from an over-budget file; whether a flagged construct is genuinely unavoidable; whether a numbering gap is deliberate. ADR-010's re-tier registry exists specifically to keep this human, and the audit's own consult-before-tiering rule is that principle applied reflexively.
3. **Whether a relationship should exist at all.** A reference-integrity gate can prove `manager-routing-guide:79` resolves; it cannot say whether one skill should reach into another skill's directory. `writing-skills:314` leaves the resolution deliberately open — *"copy it into the skill that needs it, **or** reference a sibling skill"* — **and it should stay open.**

### The failure modes of mechanization itself

This is where the cycle's own enthusiasm most needs resisting, because ICON supplies **three verified instances** and they are not the ones the roadmap naturally protects against.

**A gate can encode its author's blind spot and then verify itself against it.** `M-I-4` is the cleanest example in the corpus. ICON-0087 pinned every `uses:` to a SHA, mechanized it via a semgrep rule, codified it in a standard, and specified a **completeness grep** to prove nothing was missed. **Three layers. All three matched `uses:` only. All three were blind to `container: image:`** — which is where third-party code actually executes against the checkout. **The verification step confirmed the blind spot rather than revealing it.** This is *worse than no gate, because it manufactures justified confidence.* The general lesson: **a completeness check written by the same author as the rule inherits the rule's scope error, and no amount of rigor in executing it recovers the missing scope.**

**A gate can assert a proxy instead of the invariant.** `x-89-1`. ICON-0088 shipped a heading-count-vs-record-count cross-check into `context_template/` for **every consumer**, and it is currently green on a file that violates the cap it exists to protect. **Both domains proposing to mechanize it would have shipped the same defect.**

**A gate can be inert and nobody notices.** ADR-005's `python3 -c "import json; …"` is declared in two places as *the* validation for this repo, and `python3` on the maintainer's machine resolves to a Store stub that does not execute. The `security` CI was red for many cycles unread. `shellcheck` is not installed on the maintainer's box, so that pre-commit gate **silently skips**. **Three controls, all believed active, none of them running.**

And the structural cost, from `X-89-3`: all ten pre-commit invariants are opt-in per clone and `--no-verify`-bypassable with **no CI backstop whatsoever**. Every clean result quoted in the Tier-1 argument above is contingent on one config command.

### The design rule this yields

> **Anchored gates compound. Instance gates displace. Proxy gates lie.**
>
> - **Anchored** — derives its expected value from a source of truth (a directory listing, a script constant, a manifest, a live CI status). The README registration gate is anchored to `skills/*/` and survived a rename storm **precisely because renaming a skill changes the anchor rather than evading a pattern**. The cap-literal gate is anchored to `ENTRY_CAP=10` and cannot be routed around by rewording.
> - **Instance** — asserts a fixed string or shape. A gate banning the literal `the 15th` is satisfied by writing "fifteen." Useful, cheap, and permanently one edit from being circumvented by an author optimizing for green.
> - **Proxy** — asserts something *correlated* with the invariant. **This is the dangerous class, because it produces a green signal that reads as a guarantee.** Both current instances were written by careful authors who had just diagnosed the failure correctly.
>
> **The shipping test: before shipping any gate, state the invariant in one sentence, then ask whether the check *is* that sentence or merely correlates with it.**

That rule is falsifiable against ICON's own record, it explains why the one gate that stayed closed stayed closed, it explains both of the repo's currently-broken controls, and it supplies the **D** column in the roadmap ranking.

### Final answer, in one paragraph

Mechanization's reach in ICON is **every invariant that can be written as data, checked against a live source of truth, and run somewhere unbypassable.** That is a large fraction of this cycle's findings — considerably larger than the "no grep can see this" framing implies, because **the limiting factor is representation, not detection**. It excludes truth-about-the-world, tier judgment, and should-this-relationship-exist, and every domain correctly refused those. The abstraction-level escalation is not displacement and is not an argument against the program; it is **the signature of a detection floor rising**, and it predicts that the next two audits will report *more* findings at *higher* abstraction while the mechanical layer stays clean. **The real risks are not that gates fail to catch things** — it is that gates encode blind spots and then confirm them, that they assert proxies and read as guarantees, and that ICON's entire enforcement layer is currently one un-run config command away from being decorative. **Fix that layer (R-0b) and amend the ADR that forbids fixing it (R-0a) before building the eleventh gate.**

### Audit-process observation

Three things about how this audit ran are worth recording, because each is the audit exhibiting a class it exists to find.

**The audit's own inputs were hand-authored and unverified, and two errors reached five sub-agents** (`x-89-3`). One was a stale carry-forward premise that domain 04 had to spend part of its report refuting; the other was a scale inventory naming five maintainer-only skills while claiming three, one of which is a *shipped* skill and one of which is not in the repository at all. **Both are trivially derivable** — carry-forward status from `CHANGELOG.md`, scale from `ls` — and both are the same class as the defects the audit exists to find, occurring in the audit's own dispatch. The corrective rule is recorded at `plan.md:20` for the first and generalized here for the second: **a hand-authored baseline is a hypothesis; derive it.**

**A manager-relayed finding is a lead, not a verified fact.** The in-task `.context/` correction (commit `8de5f48`) dispatched two cited claims and produced four fixes. **One of the two cited claims was itself false** — `github-access.md:11` was already accurate and was correctly left untouched — and **two of the four fixes came from the instruction to sweep the file for the whole staleness class rather than fixing only the cited line.** The "verify against source before editing" instruction is what caught the false claim. This is the same verify-don't-assume class as the ICON-0085 retrospective entry, and it argues that dispatch briefs should carry class-sweep mandates rather than line-item fix lists.

**The finding count rose eightfold while the mechanical pass rate rose.** The natural reading — quality regression — is contradicted by the evidence, and § *The Reach of Mechanization* argues the detection-ceiling reading instead: clearing a noisy, cheap-to-find class moves the audit's marginal attention down a layer, where it finds what was always there. **The prediction this makes is falsifiable and worth recording for the next cycle: if the ceiling model is right, ICON-0090 and its successor should report *more* findings at *higher* abstraction while every gated invariant stays clean.** If instead the mechanical layer starts producing findings again, the displacement model deserves reconsideration.

## Post-Audit Verification (added after synthesis)

Two findings were tested against live behavior *after* the report was written, during this task's own close-out. Both results are recorded here rather than edited into the findings above, so the audit's original claim and its verification stay separately visible.

### `x-89-1` (retrospective log over cap) — **confirmed on the fact, corrected on the implication**

This task's retrospective append was run as a live test of the finding. Observed:

| | |
|---|---|
| Entry count before append | **11** (`grep -c '^### '`) |
| `ENTRY_CAP` in source | **10** — `skills/context-maintenance/scripts/append-retrospective-entry.sh:41` |
| Entries pruned by the append | **2** (ICON-0079, ICON-0078), both archived to `.context/retrospectives-archive.md`, not discarded |
| Entry count after append | **10** — exactly at cap |

**The fact is confirmed**: the file was one entry over cap, exactly as `x-89-1` states, and the ICON-0088 heading-vs-paragraph cross-check did report clean throughout because both counts equalled 11.

**The implication needs correcting.** The over-cap state was *not* evidence of a broken pruning mechanism. The script implements documented multi-prune convergence (`append-retrospective-entry.sh:24-26`): with a pre-insert count of 11 it computed `keep = cap - 1 = 9` and dropped `11 - 9 = 2`, landing the post-insert file exactly at cap rather than tracking one-in-one-out. The mechanism self-heals accumulated drift on the next append, and the ICON-0073 archive path worked as designed.

**Consequence for R-9**: the corrected specification stands, but its *justification* narrows. The `count ≤ ENTRY_CAP` assertion is still worth shipping — it detects the drift window between the drift appearing and the next append closing it, which is exactly when an audit reads the file and draws a wrong conclusion, as this one did. But it is a **detection-latency gate, not a correctness gate**, and it should not be sold as fixing a broken cap. Ship it at advisory, or fail-closed only if the drift window is judged to matter. The `heading_count == awk RS="" record_count` coalescing assertion is unaffected — that one remains a genuine correctness check.

This is itself an instance of the report's own thesis: the proxy-gate risk is not only that a check can be green on a violation, but that a *reader* can infer a broken mechanism from a state the mechanism was designed to absorb.
